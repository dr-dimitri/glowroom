# Local subject matting model

Glowroom runs this model natively with Core ML. Python is a developer-only conversion dependency. Photographs never leave the machine. The app's automatic-mask settings import the resulting package after provenance, interface and integrity checks.

## Prepare

On an Apple Silicon Mac with Python 3.11 and a macOS 14+ SDK:

```sh
python3.11 -m venv /tmp/glowroom-subject-env
/tmp/glowroom-subject-env/bin/python -m pip install -r tools/subject-matting/requirements.txt
/tmp/glowroom-subject-env/bin/python tools/subject-matting/check_deform.py
/tmp/glowroom-subject-env/bin/python tools/subject-matting/prepare.py \
  --source /tmp/glowroom-subject-sources --download \
  --output /tmp/GlowroomBiRefNetHR.mlpackage
```

The download is approximately 444 MB. Preparation traces on the CPU with at most eight threads because torchvision's deformable convolution has no MPS implementation. Preparation and the dependent Core ML conversion stay ordered; running them simultaneously would duplicate substantial model memory. The source and three SHA-256 values are pinned in `prepare.py`. Previously downloaded sources can be used without `--download`. A checksum mismatch fails before executing model source. No `trust_remote_code`, pickle deserialization, runtime Python or runtime network model loader is used.

The converter defaults to the approved **1920 × 1920** input. Import the generated `GlowroomBiRefNetHR.mlpackage` through Glowroom's local subject-matting setup. Model generation can require considerably more memory than app inference. Keep the sibling `.inventory.json` with qualification records; it identifies exact generated bytes. The converter canonicalizes package UUIDs and protobuf map serialization for reproducibility with the pinned tool versions. Existing 2048 installations are recognized only for controlled replacement/removal and request an update before generating a new mask; failed or cancelled replacement preserves them. Stored mask rasters remain unchanged.

Qualify it against the original PyTorch graph using an already developed, local sRGB image:

```sh
/tmp/glowroom-subject-env/bin/python tools/subject-matting/qualify.py \
  --source /tmp/glowroom-subject-sources --model /tmp/GlowroomBiRefNetHR.mlpackage \
  --image /path/to/local-developed-photo.png --output /tmp/glowroom-subject-qualification
```

This saves native/reference alpha masks, diagnostic −5 EV background renders and numeric differences. It performs a first prediction after loading a new model and a repeated prediction with that model retained. OS, Core ML and GPU caches are not flushed, so the first prediction is not a guaranteed cold-cache measurement. Reference and native process peaks are reported separately; native Python memory includes conversion libraries and the compiler, so it must not be presented as Glowroom's inference-only memory usage. The image does not leave the machine.

Reference inference runs in a child process and exits before native model loading, so PyTorch's retained CPU allocator does not overlap with Core ML's model allocation. `--reference-only` can stop after saving the reference if the native measurement will use the standalone Swift tool.

For a standalone native process measurement, compile `benchmark.swift` with `swiftc`. Pass the same developed image, `gpu` or `cpu`, and a new output directory. Prefer an already compiled `.mlmodelc` to keep compiler memory out of this process. Its input resize matches Glowroom's CoreGraphics high-quality resize, which can differ slightly from the PyTorch/Pillow bilinear resize. It saves native Float32 alpha plus timings and peak process RSS; system GPU/driver allocations are not fully represented by that RSS value. `requestSecondsToFirstValidatedAlpha` uses a monotonic clock and includes model loading, image decode/resize, the first prediction and validation/copying of its alpha. It excludes compilation, diagnostic file writes, RAW development, Glowroom's installation hashes and the final aspect-restored Gray8 raster. It therefore measures the native request, not complete app latency. An optional final argument `1` measures only the first prediction in a fresh process; omit it to also measure a repeated GPU prediction with the model retained.

```sh
swiftc tools/subject-matting/benchmark.swift -o /tmp/glowroom-subject-benchmark
/tmp/glowroom-subject-benchmark /tmp/GlowroomBiRefNetHR.mlpackage compile /tmp/GlowroomBiRefNetHR.mlmodelc
/tmp/glowroom-subject-benchmark /tmp/GlowroomBiRefNetHR.mlmodelc /path/to/photo.png gpu /tmp/glowroom-subject-gpu
/tmp/glowroom-subject-benchmark /tmp/GlowroomBiRefNetHR.mlmodelc /path/to/photo.png cpu /tmp/glowroom-subject-cpu
/tmp/glowroom-subject-env/bin/python tools/subject-matting/compare_native.py \
  --reference /tmp/glowroom-subject-qualification/reference-alpha.npy --native /tmp/glowroom-subject-gpu
/tmp/glowroom-subject-env/bin/python -m unittest discover -s tools/subject-matting -p 'test_*.py'
```

For exact graph parity, pass the `reference-input.png` saved by `--reference-only` to the Swift tool. This removes differences between Pillow and CoreGraphics resizing. The Swift tool saves `alpha-1.f32` and `alpha-2.f32` in row-major Float32 layout; the comparison gates every prediction, including the first. Non-finite values, invalid alpha ranges or shapes fail closed. Run CPU and GPU benchmarks sequentially because they share the machine's memory and compute budget.

`--side` on preparation and reference qualification accepts multiples of 32 from 256 to 2048, with **1920** as the default. Other sizes are exploratory candidates using the identical HR-trained weights; only the exact pinned 1920 package is accepted for runtime/import. The stride-32 encoder and decoder patch channels require this alignment; Swin attention windows still add padding, so speed need not scale smoothly with pixel count. The stored mask remains bounded by 2048 pixels; input resolution and saved raster dimensions are distinct.

Historical measurements on one developed RAW preview on an M2 Pro with 16 GiB RAM: the previously approved 2048 model took about 6.7 s to load plus 41.0 s for its first GPU prediction and 33.5 s for a repeated prediction with weights retained. CPU inference took 8.7 s after a 6.3 s load but differed more from the Float32 reference. An exploratory 1024 export took 6.4 s to load, 3.2 s for the first GPU prediction and 0.7 s for the repeated prediction; its wider soft needle edges were visibly worse. These figures describe the earlier workload and do not establish a general speedup or Lightroom equivalence. See the historical `qualification.json` for numerical differences and memory limits. In the app, retaining a finished mask avoids repeating inference without retaining model weights.

## Resolution experiment

The follow-up six-second experiment uses the same checkpoint, conversion precision, CPU/GPU policy and developed image for every size. Convert and compile each candidate once, then invoke the standalone benchmark serially in new processes with the final argument `1`. Reusing a completed mask or retaining an `MLModel` would measure a different task. Independent source review and lightweight diagnostic preparation can run concurrently; model conversion, native benchmarks and the subsequent app build stay ordered to avoid resource contention affecting the results.

Report every native request, its separate loading/inference times, the median and the observed range. Three observations do not establish a percentile or a latency guarantee. The first process after conversion can pay a much larger initialization cost than later new processes; keep it visible rather than discarding it. System caches are not purged. Timings from this series cannot be mixed with earlier qualification runs as if cache state were controlled. Fine-edge comparisons use aspect-restored scalar alpha and the same linear-sRGB −5 EV diagnostic at native preview pixels. Photographs and derivatives remain in private temporary directories.

On the same M2 Pro/16 GiB host, three new native processes per size produced these request times, including model loading:

| Square input side | First / second / third request | Median |
| --- | --- | ---: |
| 1024 | 3.45 / 2.44 / 2.38 s | 2.44 s |
| 1536 | 9.41 / 3.64 / 3.43 s | 3.64 s |
| 1792 | 10.53 / 4.95 / 5.17 s | 5.17 s |
| 1920 | 11.84 / 5.43 / 5.23 s | 5.43 s |

1920 was selected for the app after this experiment. It is in the approximately six-second range on a subsequent native request with populated system caches. Its first process in this series took 11.84 seconds, so it does not meet a six-second startup guarantee. The already qualified 1024 model had been used before this experiment, whereas the larger candidates were converted for this series. See [`resolution-experiments.json`](resolution-experiments.json) for all observations, controls and qualification limits; its experimental status records the historical pre-promotion state. The current app manifest and interface now require 1920.

A new 2048 control request with the same instrumentation took 33.24 seconds (one observation, not a median), including 0.72 seconds loading and 31.89 seconds prediction. A final 1024 control took 3.27 seconds, including 0.93 seconds loading and 2.09 seconds prediction: loading/cache variability remains visible even with stable prediction times. Do not extrapolate intermediate sizes from pixel count alone.

On the two inspected native-pixel needle/interior-gap crops, 1920 preserved details very similarly to the 2048 comparison; no clear systematic detail loss was visible there. 1024 had softer, wider transitions. Pointwise differences and thin bright mixed-pixel remnants under −5 EV remain, including at 2048. This single-image diagnostic does not establish a ground-truth accuracy score or replace production-renderer validation.

Separate native/Float32 comparisons use each size's exact saved reference input, excluding those extra runs from the performance series. Both 1792 and 1920 pass the existing finite/shape/range, MAE ≤ 0.01 and P99 ≤ 0.1 gates, but are not numerically identical:

| Side | Mean absolute alpha difference | P99 difference | Maximum difference |
| --- | ---: | ---: | ---: |
| 1792 | 0.00093427 | 0.02449879 | 0.20852727 |
| 1920 | 0.00199026 | 0.05388648 | 0.50255138 |

1792 was the numerically more conservative alternative: its 5.17-second median meets the time band and its native graph is closer to its own Float32 reference. This is a numerical comparison, not evidence of greater ground-truth accuracy. The selected 1920 graph is now approved; that choice and the visual similarity do not remove the reported numerical limits.

The 1920 CPU fallback also passes the existing gate against the same exact saved reference input: MAE 0.00223898, P99 0.05803692, maximum 0.44827205. One new native CPU process took 4.87 s loading and 5.82 s prediction, 11.22 s through validated alpha, with approximately 4.20 GB peak process RSS. System caches were not purged; this is a reference-input functional check rather than full app latency or CPU/GPU pixel equality.

Final integration through PicEdit's actual RAW/mask worker and the installed 1920 package took **11.62 s and 5.89 s** for two new masks, including installation verification and final Gray8 raster. The result cache was disabled; both 2048 × 1365 rasters were byte-identical. A pre-cancelled request was rejected and the original RAW stayed unchanged. Installation itself loaded the model for validation, and system caches were not flushed; RAW development and diagnostic PNG writes are excluded. [`deployment-1920.json`](deployment-1920.json) records the promoted package, fallback checks, integration results and UI verification. The in-canvas status remains visible throughout the current request, including admission/loading, and disappears on completion, failure, cancellation or source change.

## Contract

- Model: `ZhengPeng7/BiRefNet_HR-matting`, pinned revision `5d6b6f8adcb5b417c871b1d84ceaae9871355b7f`, MIT.
- Input: `image`, RGB image 1920 × 1920, sRGB, aspect stretched to the square. Core ML scales bytes by 1/255; graph subtracts ImageNet mean `[0.485,0.456,0.406]` and divides by standard deviation `[0.229,0.224,0.225]` per channel.
- Output: `alpha`, Float32 multi-array `[1,1,1920,1920]`, sigmoid foreground coverage. Restore original aspect ratio, then invert for a background mask. Preserve fractional coverage; do not threshold or erode it. The persisted raster still allows up to 2048 pixels on its long edge.
- Native compute policy: CPU + GPU. The model retains a CPU execution path. ANE is excluded because the upstream Core ML investigation observed excessive compilation time for this architecture.
- Real learned deformable convolution offsets and modulation are preserved through bilinear sampling plus 1 × 1 convolutions. `check_deform.py` checks nonzero offsets, out-of-image samples and masks against torchvision before full model qualification.
- `common::fuse_transpose_matmul` is disabled to preserve attention behavior on Apple GPU drivers. Numeric comparison of the full native model against the pinned PyTorch reference is still required for release qualification.
